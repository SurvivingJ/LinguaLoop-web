# Verification: is "en capped at 2 exercises/sense" a sandbox artefact?

Date: 2026-09-18. Read-only fact-check against repo evidence (wiki, memory
notes, `services/vocabulary_ladder/config.py`, `wiki/database/schema.tech.md`,
sandbox docs). No Supabase queries, no LLM calls, no migrations were run to
produce this file.

## 1. English coverage: production vs sandbox

**Production (repo evidence):**

- `wiki/database/schema.tech.md:273` — `dim_word_senses.definition` is
  `NOT NULL` in the production schema. A row cannot exist without a
  definition, in any language.
- `wiki/database/schema.tech.md:306` — the sense-generation prompts
  (`vocab_definition_generation`, `vocab_sense_selection`) "exist for
  zh/en/ja" — en is generated through the identical single-LLM-call pipeline
  as zh/ja, not skipped or special-cased.
- Memory note `webapp-content-inventory-2026-08.md` (2026-09-08 live
  Supabase measurement, cited in this session's task prompt and re-verified
  here): **en has 10,774 senses**, of which `has_pron` = 22 (0.2% ≈ the "~0%,
  22 senses" figure the task cites) and `has_zipf` = 92%. This table does
  **not** report a definition-null count — because the column is NOT NULL,
  a null-definition count in production is structurally impossible.
- The "en words have ZERO zh/ja glosses (0/4,222)" figure from the same
  memory note is a **different metric**: it counts *cross-language* gloss
  rows (`definition_language_id` = zh or ja, for an English headword), used
  by `cross-language-glosses` skill. It says nothing about whether an
  English headword has an **English** (`definition_language_id = en`)
  definition — that population is the 10,774-sense figure above, and it is
  the one `definition_match` actually reads for en (`same_tier_senses`
  requirement, `_CAPABILITY_SPEC` in `services/vocabulary_ladder/config.py:479`).
- Established, not conflated: **10,774 = en's own-language sense count
  (definition_match's real denominator)**; **4,222 = en's missing
  cross-language gloss count (unrelated to definition_match)**.

**Sandbox (repo evidence):**

- `sandbox/exercise-lab/README.md` §7, gap #3: *"English has no local
  dictionary at all (`db/build_db.py:load_en_vocab`). Every en
  `dim_word_senses.definition` is NULL. en lemmas come from `wordfreq`'s
  published frequency list plus tokens mined from the 76 local EN test
  transcripts... `definition_match`-style prototypes... cannot be built for
  English from this seed data without new synthesis."*
- `sandbox/exercise-lab/docs/results-zero-llm.md` §3 itself flags this
  inline: *"0% (0) — every en definition is NULL, **a pre-existing fidelity
  gap, not a new finding**."* The sandbox authors already knew this was a
  seeding gap, not a discovered production fact.
- Cross-check inside the sandbox's own second prototype:
  `sandbox/exercise-lab/docs/results-fat-seed.md` §7 marks `definition_match`
  **GREEN for en** (along with zh/ja) — because the fat-seed prototype
  synthesizes a fresh LLM definition as part of its seed call rather than
  reading the pre-seeded (and deliberately unpopulated) sandbox column. The
  two sandbox documents disagree with each other on en `definition_match`
  viability, and the zero-LLM doc's own text explains why: it is measuring
  an artefact of `build_db.py`'s English seeding path (no local en
  dictionary source was ever available to seed from), not a production
  capability limit.

**VERDICT: "en is capped at 2 exercises/sense" is an ARTEFACT of the
sandbox's English seed data, not a fact about production.** Production's
`dim_word_senses.definition` is NOT NULL by schema constraint and en has
10,774 real senses generated by the same pipeline as zh/ja; `definition_match`
is enabled for en in `_CAPABILITY_SPEC` and is a `deterministic` (zero-LLM)
generator. The sandbox's 51.3%-zero / 47.4%-exactly-2 / 0%-five-plus
distribution is real *for that sandbox build*, but it is driven entirely by
`build_db.py` choosing `wordfreq` (a frequency list with no definitions) as
en's only seed source — a documented, self-acknowledged gap, not a new
production defect.

What remains **UNVERIFIED** from the repo alone (no production number
found): the exact % of en's 10,774 senses with a non-null
`example_sentence`, and whether en senses have any stored embedding — no
schema column or memory note gives an en `example_sentence` or
sense-level-embedding coverage percentage. Do not assert a number for either.

## 2. Capability-matrix reconciliation (en's "15 enabled / 12 fat-seed types")

Verified directly against `services/vocabulary_ladder/config.py`:
- `_CAPABILITY_SPEC`: lines 475–514 (confirmed, matches the task's citation).
- `compute_active_levels`: starts line 571 (confirmed).
- Language IDs (confirmed via `Corpuses/verify_collocations.py:23-25`,
  `Corpuses/ingest_corpus.py:43-45`, `routes/corpus.py:26`): **1 = zh, 2 = en,
  3 = ja.**

Counting `is_enabled=True` rows per language directly from `_CAPABILITY_SPEC`
reproduces the sandbox's own count exactly: **zh 17, en 15, ja 18** enabled
types (matches `sandbox/exercise-lab/docs/results-fat-seed.md` §7's table,
independently recomputed here, not just copied).

En is indeed the only language with all of `collocation_gap_fill` (line
496), `collocation_repair` (line 502), and `word_family` (line 507) enabled
— those three rows list only `language_ids=(2,)` with no corresponding
enabled row for zh/ja at all. **One correction to the peer's claim:**
`morphology_slot` is *not* en-exclusive — `_CAPABILITY_SPEC` line 484-485
enables it for **both** en `(2,)` and ja `(3,)`; only zh `(1,)` is disabled
(line 486). So en's distinguishing set is 3 types (collocation_gap_fill,
collocation_repair, word_family), not 4 — the qualitative claim ("en has the
richest capability surface") still holds, just with morphology_slot shared
with ja.

**"15 prod-enabled" and "12 fat-seed-renderable" are two different axes, and
conflating them is the actual error to watch for:**
- "15 prod-enabled" = rows in `_CAPABILITY_SPEC` with `is_enabled=True` for
  en (config-level gate, independent of any seed data).
- "12 fat-seed-renderable" (`results-fat-seed.md` §7) = of those 15, how many
  the **fat-seed prototype's `render.py`** dispatch table can render from a
  freshly LLM-authored seed — a measure of that prototype's own renderer
  coverage, not of zero-LLM/deterministic status.
- Of en's 15 enabled types, only **6 have `generator: 'deterministic'`** in
  `_CAPABILITY_SPEC` (`definition_match`, `cloze_typed`, `jumbled_sentence`,
  `text_flashcard`, `listening_flashcard`, `timed_speed_round` — lines 479,
  481, 500, 509-511). The other 9 (`phonetic_recognition`,
  `cloze_completion`, `morphology_slot`, `collocation_gap_fill`,
  `semantic_discrimination`, `spot_incorrect_sentence`,
  `collocation_repair`, `synonym_antonym_match`, `word_family`) are
  `generator: 'llm'` and are **not** zero-LLM capable at all, fat seed or not.

**Reconciliation with results-zero-llm.md's "capped at 2":** the zero-LLM
doc only ever measured the 6 deterministic types for en, and of those,
`definition_match` was zeroed out by the sandbox artefact in §1 above,
leaving only `cloze_typed`/`jumbled_sentence` (both sentence-dependent) as
the surviving reachable pair — hence "2." With `definition_match` restored
(as production evidence says it should be, since en definitions exist and
`same_tier_senses` is satisfiable from 10,774 real senses), en's realistic
**zero-LLM** ceiling is **3 deterministic types**
(`definition_match` + `cloze_typed` + `jumbled_sentence`; `text_flashcard`/
`listening_flashcard`/`timed_speed_round` are marked enabled+deterministic
in config but — per `results-zero-llm.md` §3 — have **no registered builder**
in `services/vocabulary_ladder/deterministic/` at all, so they don't fire
through this path for any language, en included). This is a **repo-derived
correction**, not a live measurement: the actual % of en senses for which
`definition_match` succeeds in production is **UNVERIFIED** (would require
running the real builder against real data, which is out of scope here) —
but the "0%, capped at 2" specific number is established as wrong, and "3
deterministic types are structurally reachable" is the corrected ceiling.

## 3. Sentence-corpus and CC-CEDICT-breadth sanity checks

### 3a. Real corpus size vs the sandbox's 153 tests / 765 questions

The sandbox's sentence corpus (`sandbox/exercise-lab/README.md` §4/§5) came
from one CSV export dated **2025-12-09**
(`generated_tests_20251209_225642_*.csv`): 153 tests (76 en, 76 zh, **1**
ja) / 765 questions, plus DT gold fixtures explicitly *not* loaded.

Production repo evidence (memory `webapp-content-inventory-2026-08.md`,
live Supabase count dated 2026-08-21/22 — the most recent production test
count recorded in the repo; **not** re-verified live for this task, per the
no-DB-access constraint):

| lang | active tests (2026-08-21/22) | DT passages (2026-08-21) |
|---|---|---|
| en | 106 | 27 |
| zh | 125 | 19 |
| ja | 48 (post beginner-band cleanup; was 82 before) | 21 |

Ratio vs the sandbox's fixture: en ~1.4x, zh ~1.6x, **ja ~48x** more active
tests in production than the single ja transcript the sandbox's CSV snapshot
contained. This is on top of DT passages (19-27 more transcripts per
language) that `build_db.py` never ingested as a sentence source at all
(README §4 explicitly says the DT gold fixture "was inspected but not
loaded").

**Does this change the conclusion?** Partially, and asymmetrically:
- The **direction** is unambiguous: production's real sentence-source corpus
  is larger than what the sandbox measured against, most dramatically for
  ja (~48x by test count alone, before counting DT passages or the fact that
  the 2025-12 CSV snapshot predates several months of ja content work
  recorded elsewhere in memory).
- The **magnitude needed to overturn the qualitative conclusion is not
  plausible**: ja vocabulary is 22,426 words against a corpus that, even at
  48x more tests, is still on the order of ~50-150 transcripts — nowhere
  near enough to cover a 22k-word vocabulary by chance lexical
  co-occurrence. zh is 121,159 words (full CC-CEDICT) or a curated 23,870
  (production) against ~125-150 transcripts either way. The specific
  percentages (1.27-1.57% zh, 0.08-0.12% ja) are **UNVERIFIED at their exact
  value** — production's true ja number is almost certainly higher than
  0.08-0.12% (the 1-transcript sandbox floor is unrealistically low), but
  **"cloze_typed/jumbled_sentence are structurally scarce for zh/ja" as a
  qualitative conclusion holds** — the bottleneck is corpus size vs.
  vocabulary size by 2-3 orders of magnitude, and no plausible corpus-size
  correction closes that gap.
- Recommendation: publish the qualitative conclusion ("cloze_typed/
  jumbled_sentence are near-dead for zh/ja without new sentence sourcing"),
  but caveat or drop the specific ja percentage (0.08-0.12%) as measured on
  a 1-transcript fixture, not a production-representative sample.

### 3b. CC-CEDICT breadth bias (zh 94.5% / ja 77.8% getting 5+ zero-LLM exercises)

`sandbox/exercise-lab/README.md` §7 gap #5 (self-documented): full CC-CEDICT
is ~125k entries vs. production's curated **~23,870 zh senses**
(`docs/recon-data-surface.md` §3) — this number matches the memory-recorded
production figure (`webapp-content-inventory-2026-08.md`: zh senses =
23,870) exactly, cross-validating both sources.

**Direction and size of the bias, reasoned from the measured breakdown in
`results-zero-llm.md` §3-§4:**
- The 94.5%/77.8% headline is carried almost entirely by `definition_match`
  (99.7% zh / 99.8% ja) plus the phonology-drill types
  (hanzi_to_pinyin/pinyin_to_hanzi/tone_id_word at 94.4% zh;
  kanji_to_reading/reading_to_kanji at 77.7-80.4% ja) — all of which are
  **frequency-independent**: pinyin/kanji-reading generation and
  dictionary-definition presence do not depend on how common or obscure the
  headword is, only on whether it has valid script and an entry at all
  (which every CC-CEDICT/JMdict entry does, by construction). Broadening
  the dictionary to include rare/classical/technical entries **does not
  meaningfully depress this part of the number** — a rare CEDICT entry still
  has pinyin and a definition, same as a common one.
- The types that genuinely depend on curation/frequency
  (`classifier_match` 0.4%, `counter_match` 1.4%, `cloze_typed`/
  `jumbled_sentence` ~2%) are **already the low numbers in this measurement**
  — and breadth biases these **downward** (rarer entries are less likely to
  appear in the curated classifier/counter lists or in the tiny test-sentence
  corpus), meaning production's curated, higher-frequency 23,870-word zh
  dictionary would likely show **equal-or-better**, not worse, coverage on
  these types than the full-CEDICT sandbox measurement did.
- Net: the 94.5%/77.8% "5+ exercises" headline is **not meaningfully
  inflated** by dictionary breadth (its drivers are frequency-independent);
  if anything, restricting to production's curated dictionary would likely
  produce a **similar or slightly higher** 5+ rate, and would **improve**
  (not worsen) the already-low sentence/curation-dependent percentages. The
  premise in the task ("broader, easier dictionary") does not hold up under
  inspection — breadth is not obviously "easier" here, since the two
  categories of exercise types respond to breadth in opposite (and largely
  self-cancelling, or mildly favorable-to-production) directions. This
  reasoning is analytical, not a re-run measurement — **UNVERIFIED** as an
  exact re-measured percentage against the curated 23,870-sense set.

## 4. Other sandbox fidelity gaps that would materially change a conclusion

Cross-referencing `sandbox/exercise-lab/README.md` §7 (gaps 1-14) against
`results-zero-llm.md` and `results-fat-seed.md`:

- **Gap #1/#6 (orthographic-not-semantic embeddings, capped at top-8,000
  Zipf senses)** materially affects `results-zero-llm.md` §6's distractor
  comparison (EMBED vs NONEMBED) — the "0.0 mean overlap" and ">0.92 cosine
  for 1.2% of senses" findings describe an orthographic proxy standing in
  for real semantic embeddings, and are explicitly and correctly caveated
  in the doc itself as a lower bound. This caveat is already present and
  adequate — no action needed beyond keeping it attached whenever that
  number is cited.
- **Gap #4 (zh/ja definitions are English-language glosses from
  CC-CEDICT/JMdict, not native-language definitions)** is not surfaced as a
  caveat anywhere in `results-zero-llm.md`'s `definition_match` 99.7%/99.8%
  figures. Production supports same-language (e.g., zh-defining-zh)
  definitions for native-reading learners; the sandbox's zh/ja
  `definition_match` numbers measure only the English-gloss case. If
  production serves same-language definitions for zh/ja `definition_match`
  by default, the sandbox's 99.7%/99.8% is validating a different (English-
  gloss) code path than what a native-reading zh/ja learner would see. This
  should be called out as a caveat on the zh/ja `definition_match` numbers,
  not just on the en case. **UNVERIFIED**: which definition-language
  variant production actually serves by default for zh/ja `definition_match`
  — not established from the files read for this task.
- **Gap #7 (simple/standard definition levels byte-identical for zh/ja)**
  is not called out in `results-zero-llm.md`'s `definition_match` numbers
  either, though it plausibly does not affect the pass/fail rate measured
  there (only content differentiation across the two age-tier levels), so
  it is a lower-priority caveat than gap #4.
- **Gap #5 (CC-CEDICT breadth)** — see §3b above, already reasoned through.
- **Gap #9 (empty `vocab_sense_ids`/`vocab_token_map`)** does not appear to
  affect either results doc directly (neither measurement path reads those
  fields), so no correction needed there.

No fidelity gap was found that would flip the **zh/ja `definition_match` and
phonology-drill "near-universal" conclusion** — those numbers are built on
real CC-CEDICT/JMdict data and real deterministic production code, and the
only live caveat (gap #4's English-gloss-only content) affects *what kind*
of definition is being counted, not *whether* one exists.
