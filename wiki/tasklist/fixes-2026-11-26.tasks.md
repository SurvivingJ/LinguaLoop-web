## TASK-1253: Keep `llm_calls` small: archive it to Storage regularly

**Status:** Done (repo) 2026-11-27 — runs once deployed
**Type:** infra
**Complexity:** S
**Depends On:** none

**Description:** Owner 2026-11-27: "Can we move the LLM calls table data into storage?" — done once
(51,489 rows, 46 MB → 3.1 MB; [[database/schema.tech]] `llm_calls`). The table refills at ~4,000
rows per test-generation run (~30,000 on a heavy seeding day, ~0.8 KB each with indexes). Either
run `python scripts/archive_llm_calls.py --apply --delete` weekly and then
`VACUUM (FULL, ANALYZE) public.llm_calls;`, or schedule it (the delete needs no owner review once
the archive check passes; the VACUUM FULL takes a brief exclusive lock).

**Done:** owner "Yes, set it up on a schedule". Job `llm_calls_archive_weekly` in
`web/scheduler.py`, Sundays 03:40 UTC → `services/llm_calls_archive.run_weekly`: keeps the last
`LLM_CALLS_ARCHIVE_KEEP_DAYS` (3) whole UTC days, archives the rest with the same checks as the
script, deletes them. Cross-worker: a Storage claim object per cutoff
(`llm_calls/locks/cutoff_<cutoff>.json`, created once; a second create is refused), so no
migration is needed. No VACUUM FULL (not possible through PostgREST): the freed space is reused, so
the table stays at about its busiest week. Verified live: the job skips with nothing older than
3 days; Storage refuses a second object at an existing path without overwriting.
Tests: `tests/test_archive_llm_calls.py` (11), `tests/test_platform_scheduler.py`.
