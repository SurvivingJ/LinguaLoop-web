# Test Generation — 20-Test Run: Cost and Wall Clock

**TASK-730.** First end-to-end measurement of the test-generation pipeline with the
fail-closed judge guard live (TASK-727/728/729). The question this answers: what does a
large test-generation run cost, and how long does it take?

**Headline: $0.0088 and 2.9 minutes per test. Spend is a non-issue; wall clock is the
constraint, and 82% of it is vocabulary enrichment, which is 16% of the spend.**

## Run parameters

| | |
|---|---|
| Command | `python -m scripts.run_test_generation_cli --language en --count 20` |
| Language | `en` only — see [Caveats](#caveats) |
| Type | `listening` (default; includes Azure TTS + R2 upload) |
| Difficulty | balanced, default `[1, 3, 6, 9]` — 5 tests each |
| Window (UTC) | 2026-08-20 14:24:48 → 15:23:50 |
| Result | **20 generated, 0 failed, 0 vocab shortfalls** |

Judges ran live (v3 entailment, v6/v4 distractor). The staged `test_distractor_plausibility`
v7 rows stayed `is_active = false` and were not touched.

### Three traps in this query, not one

1. **Judges log under `judge_<name>`**, not their `prompt_templates` task_name
   (`test_distractor_plausibility`). Querying the prompt-template name returns zero rows for
   a perfectly healthy judge.
2. **`pipeline = 'test_gen'` is not the whole bill.** Vocabulary sense generation, which
   test generation triggers once per test, logs under **`pipeline = 'vocab_senses'`**.
   Filtering on `test_gen` alone undercounts every test by 16%.
3. **Half the judge rows are not calls.** `log_judge_verdict` writes a zero-cost row per
   verdict alongside the billed call, so `count(*)` on `judge_%` reports 162/165 where the
   real call counts are 81/82. Costs are unaffected; call-volume claims are not. Count
   `where cost_usd > 0`.

```sql
select pipeline, task_name,
       count(*) filter (where cost_usd > 0) as billed_calls,
       round(sum(cost_usd)::numeric, 6) as cost
from llm_calls
where created_at >= '2026-08-20T14:24:48Z'
  and created_at <= '2026-08-20T15:24:30Z'
group by 1, 2 order by 4 desc nulls last;
```

**Not included:** Azure Speech TTS and R2 storage, which are not logged in `llm_calls`. The
run synthesised **16,903 characters** of audio (845 chars/test average) across 20 listening
tests. At neural-TTS list rates this is cents, not dollars, but it is a separate bill and
this number is the input for pricing it.

## Wall clock

**3,532 s total = 58 min 52 s for 20 tests → 176.6 s/test mean, 118 s median.**
The mean is well above the median because difficulty drives duration hard.

| Stage | Total | Mean/test | Share |
|-------|------:|----------:|------:|
| Vocabulary enrichment (senses, token map, per-question sense_ids) | 2,900 s | 145.0 s | **82.1%** |
| Questions + judges | 377 s | 18.8 s | 10.7% |
| Audio (TTS + upload) | 186 s | 9.3 s | 5.3% |
| Setup + prose + title | 58 s | 2.9 s | 1.6% |

| Difficulty | n | Mean | Individual runs |
|-----------|--:|-----:|-----------------|
| d1 | 5 | 49 s | 27 48 60 57 55 |
| d3 | 5 | 117 s | 104 183 87 121 88 |
| d6 | 5 | 182 s | 118 149 58 273 311 |
| d9 | 5 | 358 s | 108 130 666 422 464 |

A d9 test takes **7.3×** as long as a d1 test, because a longer passage means more unique
lemmas needing senses. The 1,209 senses linked across 20 tests cost only 390 LLM calls —
`prefer_existing=True` reuses everything the corpus already knows, so per-test vocabulary
time falls as the corpus grows. A large run therefore gets *faster* per test as it proceeds;
these numbers are an upper bound on a warm corpus, not a constant.

## Extrapolation

| Scale | Cost | Wall clock (at this run's mix) |
|-------|-----:|-------------------------------:|
| 20 tests (measured) | $0.175 | 59 min |
| 100 tests | ~$0.88 | ~4.9 h |
| 1,000 tests | ~$8.75 | ~49 h |
| 1,000 tests, all d9 | ~$13 | ~99 h |

**Spend is not a constraint at any scale we would plausibly run.** $8.75 for a thousand
tests is below the noise floor of this project's monthly LLM bill. The constraint is wall
clock, and it is the same shape as the TASK-515 sense-generation batch economics:
the blocker is time, not money. A thousand-test run is a two-day unattended job, and
sequential — one process, one language at a time.

## Yield

A cost number without a yield number is not a go/no-go.

| | |
|---|---|
| Tests generated | **20 / 20** (0 failed) |
| Questions saved | **94** of ~100 slots (4.7/test) |
| Question slots lost after retries | 6 (`Exhausted N attempts`) |
| Judge hard rejects | 2 answer-entailment, **0 distractor-plausibility** |
| Validator rejects (regenerated) | 17 |
| Questions flagged for review | **5** (5.3% of saved questions) |
| Vocabulary senses linked | 1,209 |
| Vocab shortfalls | **0** — every test complete |
| Funnel starvation events | 0 |

Two things worth noting. **The distractor judge rejected nothing in 81 calls**, consistent
with the ~0.9% production-weighted reject rate measured in
[[evaluations/distractor-gold-frame-2026-08-19]] — at 81 calls, zero is the expected count,
not a sign the judge is inert (the guard tests in `tests/test_test_gen_fail_closed.py` are
what prove it is not). And **the validator, not the judges, is what rejects questions here**
— 17 validator rejections against 2 judge rejections.

**5 of 20 tests were never judged at all**, by design: `run_judges = difficulty > 2` skips
the judges at d1/d2, where toddler passages make distractor plausibility a category error.
In a balanced `[1,3,6,9]` run that is 25% of tests. Worth knowing before reading the judge
share of spend as coverage.

## Guard behaviour in a real run

The run is also the first live exercise of TASK-727's wiring. `run_batch` executed entirely
inside `batch_mode()`, 163 billed judge calls succeeded, and nothing aborted — the guard
costs nothing when the judges are healthy. Its behaviour when they are not is pinned by
`tests/test_test_gen_fail_closed.py`, including the proof that the suite goes red when
either half of the fix is reverted.

## Caveats

- **English only.** zh and ja use different question models, and zh additionally generates a
  pinyin payload per test. Per-test cost and time will differ; the model prices in the table
  above are the input for a per-language estimate, but this run does not measure them.
- **Listening type only.** A `reading` run drops the audio stage (5% of wall clock) and the
  TTS bill entirely.
- **Warm vocabulary corpus.** See the note under Wall clock — a cold corpus is slower.
- Timing is derived from log timestamps between stage markers, so the four stage figures
  include the small gaps between them; they sum to 3,521 s of the 3,532 s total.
