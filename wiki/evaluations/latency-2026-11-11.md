# Latency audit and fixes — 2026-11-11

Measurement for [[decisions/ADR-042-request-scoped-caching-and-static-asset-caching]]
([[tasklist/latency.tasks]], TASK-925–929; follow-ups TASK-930–933). Gunicorn concurrency was
deliberately left alone (developer: hobby-tier Railway). The DB migration was applied live by
the developer on 2026-11-11 and verified (below).

**Production estimate.** Here every Supabase round trip costs ~280 ms (sandbox egress proxy);
from Railway it was measured at 53–108 ms (TASK-774). With ~60–100 ms per call, the call-count
cuts alone take ~0.4–0.6 s off the daily session GET, ~0.6–1 s off practice and ~0.5–0.9 s off
the study plan GET, on top of the SQL savings (55 ms per timezone lookup, several per request).

## Method

All runs use the dedicated **test account** (Japanese, language 3, has a live week plan) and
the **live** Supabase project.

- **SQL, server-side** — each function called 30× (build_daily_session 15×) inside one `DO`
  block timed with `clock_timestamp()`, which ends in `RAISE EXCEPTION` so every write is
  rolled back (`data/eval/latency-2026-11/harness/sql_bench.sql`). No network in the number.
- **HTTP** — the real Flask app (`create_app`) in-process with auth stubbed locally (no token
  minted), every outbound Supabase call timed (`harness/bench.py`): 1 discarded warm-up, then
  30 samples per endpoint. **Absolute times are inflated:** this container's round trip to the
  ap-southeast-2 project is ~280–700 ms through an egress proxy, against the 53–108 ms recorded
  from production (TASK-774). Read the DB-call counts and the relative change; production time
  ≈ calls × ~60–100 ms + SQL time.
- **Browser** — Chromium (Playwright), gunicorn with 2 sync workers on localhost (as in the
  `Procfile`), a session minted for the test account. Each page loaded 10× in a fresh
  context (cold cache) and 10× in one context (warm cache) (`harness/browser_bench.js`).
  Metric "data ready" = navigation start → end of the last `/api/` response. jsdelivr/cdnjs
  are blocked in the sandbox, so Bootstrap / Font Awesome are served from their npm packages
  (SRI hashes verified identical); Google Fonts are stubbed. Same setup before and after.
- **Mobile-throttled browser** (`harness/throttle_bench.js`) — the realistic run: Chromium's
  network emulation at Lighthouse "Slow 4G" (150 ms RTT, 1.6 Mbps down, 750 Kbps up), 10 cold
  (fresh context) + 10 warm (same context) loads per page, **without** request interception
  (Playwright's interception disables the HTTP cache, which made the warm column of the plain
  browser run meaningless). CDN hosts are mapped to a closed port in both runs. Both runs used
  the migrated database, so this table isolates the **code** changes.
- **Warm cache, unthrottled** (`harness/warm_bench.js`) — counts static files served from the
  browser cache vs revalidated.
- **Correction (found later the same day, while measuring TASK-933):** in the
  throttled and warm-cache runs, Chromium still sent traffic through the
  sandbox's egress proxy, so the "closed port" mapping never applied: jsdelivr and
  cdnjs were refused by the proxy and Google Fonts came from the real internet.
  Bootstrap and Font Awesome were therefore missing in BOTH runs (unstyled pages).
  The data-ready times and byte counts compare like with like and stand; they say
  nothing about styled first paint. TASK-933's measurement forces direct
  connections (`--proxy-server=direct://`, proxy env vars removed) and serves the
  third-party files from a local HTTPS mock with connection-setup delay.
- Scheduler disabled for every local server (`DISABLE_SCHEDULER=true`). The first two local
  runs had it enabled by mistake; every job is cron-scheduled at 03:50–04:15 UTC (one Sunday
  23:00) and those runs were 23:50–00:15 UTC on a Tuesday night, so nothing fired (logs show
  jobs registered, none run).

Raw samples: `data/eval/latency-2026-11/results/*.json`.

## Findings (what the numbers say)

1. **Every timezone-dependent SQL function sits on a ~55 ms floor**, which is
   `resolve_plan_timezone` scanning `pg_timezone_names` (its first call on a connection:
   300–500 ms). `now() AT TIME ZONE …` itself costs 0.05 ms. `pg_stat_statements` means:
   `apply_attempt_timing_and_progress` 506 ms, `build_daily_session` 570 ms,
   `record_session_progress` 216 ms, `review_governor_state` 177 ms, `credit_study_time` 144 ms.
2. **Request time ≈ the sum of sequential DB calls.** study-session made 20, practice 28,
   study-plan 16 — with the plan row read 4–6×, the new-word state (two RPCs) 2–3×, and
   `dim_test_types` 6×.
3. **Warm loads are as slow as cold ones**: nothing static was cacheable (Flask default
   `no-cache`) or compressed; pages waited for `/api/metadata` and serial i18n fetches; the
   session page imported every player before asking for the session.
4. Batch content generation dominates total DB time on a small instance (`shared_buffers`
   224 MB) — TASK-931.

Call counts after the code changes alone (traced with `harness/trace.py`, live DB):
study-session **20 → 14**, practice/session **28 → 19**, study-plan **16 → 8**.

## Results (before → after)

The plain browser tables use request interception (CDN files served from npm) and an
unthrottled localhost link: static files cost nothing there and API time is dominated by the
~280 ms DB round trips, so pages without DB-call cuts show no change (±5% is run-to-run noise).
Their "warm" column is not a warm-cache measurement (interception disables the cache); use the
throttled and warm-cache tables for those effects. The plain browser and HTTP "before" ran
against the pre-migration DB; the throttled "before" against the migrated one.

## DB migration verification (live, after apply)

- `tz_names`: 1,194 rows; `resolve_plan_timezone` returns the same value as the old scan for
  **all 1,205 inputs** tested (every `pg_timezone_names` name plus `''`, blanks, NULL,
  lower-case, abbreviations, POSIX offsets, garbage) — 0 mismatches.
- RLS: 106 policies; digest after unwrapping `( SELECT auth.x() AS x)` → `auth.x()` equals the
  pre-migration digest `9de38a5b2b08aef7f7062e70060c543a`; 0 unwrapped calls left.
- Indexes: 4 duplicates gone, 18 FK indexes present. Advisor: `auth_rls_initplan` 88 → 0,
  `duplicate_index` 4 → 0, `unindexed_foreign_keys` 55 → 37 (remaining ones point at
  never-deleted lookups, by design); `unused_index` 52 → 63 (the new FK indexes serve deletes,
  which have not happened yet); `multiple_permissive_policies` 372 unchanged (TASK-932).
- `resolve_plan_timezone` ACL unchanged (`postgres`, `service_role`); `tz_names` RLS on.

## Browser walkthrough (test account, new code)

`harness/walkthrough.js` — 16/16 checks pass (`results/walkthrough_after.json`):
expired token → exactly one renewal, no 401s; server-rejected token → three parallel 401s share
one renewal, data loads; daily session starts and mounts the first player (only the players in
today's queue were fetched); practice drill item renders and an answer gets feedback; preview →
test fetches `/api/tests/test/<slug>` once (hand-off), a reload fetches fresh data; switching
the UI to Japanese translates and survives reload with versioned i18n files; tests, preview,
test, session, study plan, prestudy, flashcards, profile and word list load with no console
errors, no 4xx/5xx and no raw i18n keys. Also checked by hand: a full reading-test submission
(score shown; DB has `duration_ms`, the weekly-plan progress entry and the study-time ledger row —
the path through the new `resolve_plan_timezone`); the listening intro modal (after clearing the
test account's seen flag, which the before-screenshots had used up); calibration.

**Regression found and fixed before shipping:** with the metadata round trip gone and the
preview hand-off making test data instant, the test page rendered raw keys (`test.level`,
`test.question_of`) because it drew before the translations arrived. `LinguaMetadata.load()`
now also waits for i18n (≤ 4 s), and the test / preview / session pages fetch data in parallel
and await translations only before rendering. Pinned by `tests/unit/lingua-metadata.test.js`
(fails on the buggy version, passes on the fix).

**Pre-existing bug found and fixed:** on `/profile`, `selectLanguage` highlighted cards by index
across *all* `.language-card` elements, so depending on which section loaded first it lit up
中文 under "Native language" (still "Not set") and left the study language unhighlighted —
reproduced on the old code (2 of 3 loads). Scoped to `#languageList`.

**Visual diff.** 22 full-page screenshots (11 pages × desktop/iPhone 13). Same data, old vs
new code: 19 identical; calibration ×2 differ only by its random word; the profile differs by
the fix above. (Against the morning's baseline more pages differ, all from data the walkthrough
created on the test account: 2 reading tests done, 7 flashcards due, attempt counts.)
